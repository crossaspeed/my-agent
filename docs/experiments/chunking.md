# 分块策略实验：PPT 课件该切多大

固定条件：同一批 60 条标注 query、BGE-M3 向量、同一门禁（`MIN_RETRIEVE_SCORE=0.35`）、不开重排。
只改分块参数，看检索质量如何变化。

## 结果

| 配置 | 边界 | 目标/上限 | 块数 | 均长 | Top1 覆盖 | Top3 覆盖 | Hit@1 | Hit@3 | 静默错误 | 误纳率 | 单条耗时 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| C 按页断开 | slide | 600 / 900 | 421 | 138 | 0.100 | 0.350 | 0.100 | 0.400 | 24 | 0.700 | 352 ms |
| B 按标题断开 | heading | 600 / 900 | 233 | 260 | 0.300 | 0.525 | 0.425 | 0.650 | 14 | 0.550 | 239 ms |
| A 现状（按字数） | size | 600 / 900 | 134 | 499 | 0.500 | 0.750 | 0.475 | 0.775 | 9 | 0.500 | 226 ms |
| **D 按字数（放大）** | size | **900 / 1200** | **88** | **723** | **0.625** | **0.800** | **0.625** | **0.850** | **6** | 0.500 | 146 ms |
| E 按字数（更大） | size | 1200 / 1500 | 70 | 890 | 0.500 | 0.775 | 0.600 | 0.825 | 7 | 0.500 | 134 ms |

> Top1/Top3 覆盖：以 A 档 gold 的**字符区间**为真值，判断返回块覆盖了答案文本多少（≥50% 记命中）。
> 这个口径不受 chunk id 变化影响，是五档之间唯一严格可比的指标；Hit@1/Hit@3 是各自 gold 集合上的结果
> （切得越细 gold 集合越大，id 口径会偏宽松，所以不能跨档比较）。

## 结论

1. **不是“越细越好”或“越粗越好”，而是一个峰值。** 平均块长 138 → 260 → 499 → **723** → 890，
   Top1 覆盖依次为 0.100 → 0.300 → 0.500 → **0.625** → 0.500，在 700~750 字附近最优。
2. **切细反而更差，而且差得很明显。** 按页断开后平均仅 138 字（PPT 单页本来就短），
   门禁命中率跌到 7.5%、误纳率升到 70%——短块语义信号太弱，相关度分数失去区分度。
3. **按标题断开（233 块 / 260 字）同样不如现状。** 这批 PPT 标题很碎（73 个标题），
   “一节一块”只有 260 字，仍然偏短。
4. **放大到 900/1200 是这轮唯一有效的调整**：Hit@1 0.475→0.625、Hit@3 0.775→0.850、
   静默错误 9→6，耗时还从 226ms 降到 146ms（候选块变少、向量检索更省）。
5. 再放大到 1200/1500 开始回落：一块塞进多个知识点，top1 覆盖整段答案的比例下降。

## 为什么和最初设想相反

原假设是“PPT 一页一个知识点，按页切更精准”，实测否定：

- PPT 单页平均只有 138 字，**按页切等于把每个要点切散**，命中的那块往往只有半句话；
- 短块让 embedding 的语义信号变弱（同样查询下相似度分布更平），门禁随之失效；
- 600~900 字的块恰好覆盖“一个小节 + 上下文”，既够长又不混主题。

也就是说，**“邻块命中”不是切分粒度的问题，而是块内上下文不足的问题**。
把块做大之后静默错误从 9 降到 6，邻块现象自然减少。

## 复现方式

```bash
# 1) 改参数并生效（改分块参数不需要 rebuild，但必须重新解析，不是 reindex）
sed -i 's/^CHUNK_TARGET_CHARS=.*/CHUNK_TARGET_CHARS=900/' .env
sed -i 's/^CHUNK_MAX_CHARS=.*/CHUNK_MAX_CHARS=1200/' .env
docker compose up -d api worker-io worker-llm

# 2) 对 4 份文档逐一点「重新解析」，然后迁移 gold 并重跑
python /tmp/remap_cases.py --course-id 8 --old /tmp/ranges-A.json \
    --cases /tmp/cases.csv --out /tmp/cases-new.csv
python /tmp/retrieval_bench.py --cases /tmp/cases-new.csv --course-id 8 --out /tmp/bench.json
```

`remap_cases.py` 用 chunker 记录的字符区间做交叠匹配，所以重新分块后 **gold 不需要重标**。

## 局限

- 只有 1 门课、4 份 PPT、60 条 query；峰值位置（700~750 字）**不能直接外推**到其他课程；
- PPT 与 PDF/Word 的最优块长不同：PDF 正文密度高，600 字可能已经合适；
- 覆盖口径以 A 档 gold 区间为真值，若原始标注本身有偏差，结论也会跟着偏。

## 补测：开重排之后（2026-11-12）

上面的五档都是 `rerank=off` 的纯检索结果。为了看“切块”和“重排”是否叠加，补跑了两档的重排版：

| 分块 | 无重排 Hit@1 | 无重排 Hit@3 | 重排 Hit@1 | 重排 Hit@3 | 重排静默错误 | 重排耗时 |
|---|---|---|---|---|---|---|
| 600/900（134 块） | 0.475 | 0.775 | 0.675 | 0.900 | 4 | — |
| **900/1200（88 块）** | **0.625** | **0.850** | **0.750** | **0.950** | **2** | 2088 ms |

按篇章分（900/1200 + 重排）：字面 0.867/1.000、跨语言 0.700/1.000、口语 **0.667/0.867**。

**结论修正：两者是部分重叠的收益，不是简单叠加。**

- 只换切块：Hit@1 +15.0 个点（0.475 → 0.625）
- 在此基础上再开重排：+12.5 个点（0.625 → 0.750）
- 但若切块仍是 600：重排能到 0.675。也就是说**重排能补回约一半的切块损失**，
  切细造成的损失并非不可挽回——这也是为什么“只有预算做一件事”时，先开重排、再调切块更划算。

误纳率两档都稳定在 0.500，说明它是**门禁阈值**问题，与切块、重排都无关。
