# 查询改写实验：让口语提问对上课件术语

固定条件：900/1200 分块（88 块）、BGE-M3、LLM 重排、同一批 60 条标注。
变量只有一个：检索前是否用 LLM 把口语问题改写成课程术语（`QUERY_REWRITE_ENABLED` + `--rewrite`）。

## 一、做法

`app/rag/query_rewrite.py`：

- 用 DeepSeek（temperature=0）把问题改写成“课件里可能出现的说法”，输出 `{"rewritten", "terms"}`；
- **只改查询、不改语料**；不回答、不解释；
- 任一环节失败（超时/格式错/空结果）**静默退回原查询**，检索不会因此失败；
- 进程内 LRU 缓存 512 条（同一问题重复提问很常见，第二次不再调用 LLM）；
- 开关两层：`QUERY_REWRITE_ENABLED`（全局）+ `retrieve(use_rewrite=...)`（调用点声明）。

## 二、结果（阈值同为 0.55）

| 指标 | 不改写 | **改写** | 变化 |
|---|---|---|---|
| Hit@1 | 0.750 | **0.800** | +5.0 |
| Hit@3 | 0.950 | **1.000** | +5.0 |
| 误拒率 | 0.050 | **0.000** | −5.0 |
| 误纳率 | 0.150 | **0.300** | **+15.0** |
| 静默错误 | 2 | **0** | −2 |
| 门禁命中 | 0.750 | **0.800** | +5.0 |
| 单条耗时 | 2087 ms | **3135 ms** | +1048 ms |

分类别：

| 类别 | 不改写 Hit@1/Hit@3 | 改写 Hit@1/Hit@3 |
|---|---|---|
| 口语 | 0.667 / 0.867 | **0.733 / 1.000** |
| 跨语言 | 0.700 / 1.000 | **0.800 / 1.000** |
| 字面 | 0.867 / 1.000 | 0.867 / 1.000 |
| 领域外 | 误纳 0.150 | **误纳 0.300** |

**一句话：改写把“该答的”几乎全答对了（Hit@3 100%、零误拒、零静默），代价是“不该答的”多答了一倍。**

## 三、改写样例（口语类 15 条全部改写成功）

| 原问题 | 改写后 | Hit@1 |
|---|---|---|
| 网络为什么会堵车 | 网络拥塞产生的原因 | ✅ |
| 两台机器…为什么要先对暗号 | 两台主机数据传输前为何需三报文握手 | ✅ |
| 接收窗口变成 0 之后双方会不会一直死等 | 接收窗口为 0 时是否发生死锁及零窗口探测机制 | ✅ |
| 手机连上 wifi 自动就有地址是谁给的 | 移动终端接入无线局域网后自动获取 IP 地址的协议机制 | ✅ |
| 一个 IP 包太大过不去会怎么办 | IP 数据报超过 MTU 时的分片与重组机制 | ✅ |

## 四、误纳翻倍的原因（重要）

改写不只提高召回，**也提高了“跑题问题的相关度”**：它会把“Vue 的响应式原理”这类问题写成更像课件语言的形式，
于是这些问题的 `relevance` 从 0.5 附近升到 0.6~0.7，越过阈值。

被误纳的 6 条（阈值 0.55）：

| 查询 | 相关度 | 未登录词率 |
|---|---|---|
| 数据库 B+ 树索引的分裂过程 | 0.711 | 0.22 |
| Vue 的响应式原理 | 0.667 | 0.17 |
| 快速排序的平均时间复杂度 | 0.651 | 0.56 |
| 有监督学习和无监督学习 | 0.603 | 0.33 |
| 编译原理中 SSA 形式 | 0.575 | 0.40 |
| 5G 和 4G 在物理层 | 0.564 | 0.40 |

注意：这些问题的**未登录词率都低于 0.5**（“数据库/索引/物理层/学习”这些词课件里都有），
所以“词表门禁”对它们本来就无效——用原查询的未登录率重算，误纳率依然是 0.300（已实测验证）。
**这是词表门禁的固有盲区，不是改写引入的新问题，但改写把它放大了。**

## 五、能不能两全：改写 + 提高阈值

| 配置 | 误拒率 | 误纳率 | 静默 | Hit@3 | 单条耗时 |
|---|---|---|---|---|---|
| 不改写 + 0.55 | 0.050 | 0.150 | 2 | 0.950 | 2087 ms |
| 改写 + 0.55 | 0.000 | 0.300 | 0 | 1.000 | 3135 ms |
| **改写 + 0.60** | **0.000** | 0.200 | 0 | 1.000 | 3135 ms |
| 改写 + 0.65 | 0.050 | 0.150 | 0 | 1.000 | 3135 ms |

- **改写 + 0.60**：零误拒（“该答的一定答”），比不改写多放行 1 条跑题问题；
- **改写 + 0.65**：错误率与不改写持平，但 Hit@3 从 0.95 升到 1.00、静默从 2 降到 0。

## 六、建议（按场景）

| 场景 | 建议 | 理由 |
|---|---|---|
| 导学（学生提问） | **开改写 + 阈值 0.60** | 学生用口语提问，拒答体验最差；多放行 1 条跑题可以接受 |
| 出题 / 阅卷 | **不开改写**（或开改写但阈值 0.65） | 依据必须严格在考纲内，误纳会直接产出跑题题 |
| 评测 / 调试 | 可开 | 便于观察改写质量 |

**当前状态：`QUERY_REWRITE_ENABLED=false`**（代码与实验已就绪，默认不启用）。
启用方式：

```ini
QUERY_REWRITE_ENABLED=true
MIN_RETRIEVE_SCORE=0.60   # 配合改写使用
```
然后在需要改写的调用点传 `use_rewrite=True`（目前只有评测脚本传）。

## 七、局限与下一步

- 只在 60 条样本上验证，其中口语仅 15 条；
- 改写本身没有评估（没有“改写正确率”这个指标），只看端到端检索效果；
- 真正的解法是**第二次判定**：改写负责召回，另用一次 LLM 判断“候选片段能否回答这个问题”，
  这样既保留召回又压住误纳——预计能把误纳压到 10% 以下，代价是每问多一次调用（约 0.8 s）。
- 也可以做“按需改写”：只对未登录词率高、或查询很短的问题改写，减少 1 s 的固定开销。
